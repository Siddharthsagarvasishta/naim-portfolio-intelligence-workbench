# nAIM security threat model

Last reviewed: 2026-08-01  
Scope: local workbench, API, browser client, governed onboarding, workflow database, generated artifacts, and optional integration boundaries.

## Security posture in one sentence

nAIM provides tested application-level safeguards for a synthetic-data workbench, but it is not a certified production security boundary: production use still requires enterprise identity, managed secrets, hardened storage, network controls, malware scanning, centralized audit retention, monitoring, and incident response.

## Assets and security objectives

The assets in scope are portfolio aggregates and detail, source files, source and artifact hashes, metric/configuration versions, scenario assumptions, workflow and approval state, audit events, access tokens, generated Office/BI packages, and deployment configuration. The objectives are:

- confidentiality: only an authenticated principal with the backend permission may retrieve an artifact or governed detail;
- integrity: source, metric, scenario, workflow, and artifact changes must be traceable and tampering must fail closed where implemented;
- availability: bounded requests, uploads, parsers, and rate limits should prevent a single request from exhausting a local deployment;
- analytical integrity: calculations must use governed definitions and point-in-time data, and recommendations must remain draft decisions requiring human review;
- provenance: outputs must carry source context, configuration/run identifiers, limitations, and checksums where the format supports them.

## Trust boundaries and principal flows

1. A browser or API caller crosses the network boundary into FastAPI. CORS is not authentication; bearer/OIDC or demo authentication and backend permissions remain authoritative.
2. An uploaded file crosses from untrusted user storage into the onboarding quarantine. It is not loaded into active analytics until parser, contract, reconciliation, and approval checks pass.
3. Configuration and scenario inputs cross from a user-controlled request into deterministic calculations and durable workflow state. Typed bounds, role checks, version checks, and approval state constrain this flow.
4. Generated artifacts cross from governed calculation code into a filesystem-backed export registry. File name containment, expiry, SHA-256/size revalidation, a scoped download token, and download auditing constrain retrieval.
5. Optional OIDC, PostgreSQL, licensed market-data, Power BI, Tableau, SAS, Sites, and external-language-model connections cross an institutional or vendor boundary. Those adapters are not production-validated in this release unless their capability status explicitly says otherwise.

## Assumptions

- `NAIM_AUTH_MODE=disabled` is restricted to a private local development machine. It grants a local Administrator principal and is unsafe for a network-exposed deployment.
- Filesystem and database administrators are trusted. Hash chaining detects ordinary database-event alteration, but it is not a signature or externally anchored ledger.
- HTTPS termination, host hardening, encryption at rest, backup protection, centralized logging, and key rotation are deployment responsibilities.
- Demonstration data are synthetic. This reduces privacy impact but does not make the code suitable for ungoverned real customer data.

## Control limitations that must remain visible

- Rate limiting is an in-process sliding window. It is suitable for a local/single-node service, not a distributed denial-of-service control.
- CORS is an origin-response control, not identity or CSRF protection. The API permits explicit origins and credentials are disabled.
- The API adds restrictive CSP, `nosniff`, frame denial, referrer, permissions, cache, request-ID, and data-mode headers. HTTPS/HSTS belongs at the production ingress and was not validated here.
- Demo tokens and download tokens expire and are scoped, but real OIDC issuer/JWKS/claim behavior was not tested against an identity provider.
- The workflow audit chain detects changes relative to its stored hash chain. It is not append-only against a database administrator and is not externally anchored.
- Safe temporary directories use context-managed cleanup, and failed onboarding uploads remove their generated directory. Abrupt process termination can still leave generated export files or temporary remnants for operating-system cleanup.

## Production acceptance gates

Do not expose nAIM to real portfolio data or an untrusted network until all of the following are independently evidenced:

1. OIDC is tested against the target IdP, roles are least-privilege, disabled auth is rejected outside local development, and maker-checker approval is enforced.
2. HTTPS/HSTS, network policy, centralized rate limiting, WAF/abuse monitoring, and security logging are active.
3. Secrets are in a managed store; repository and Git-history scans, dependency advisory audits, SAST, container/image scans, and rotation exercises pass.
4. Uploads and downloads pass antivirus/DLP controls; parsers run with tighter CPU/memory/time limits; object storage is immutable/versioned.
5. Audit events and signed artifact manifests are retained in a protected external system with alerting and tested incident response.
6. Live vendors, PostgreSQL, BI publishers, and deployment targets complete threat review, credential review, data-residency review, and failure-mode testing.

## Review triggers

Repeat this threat model whenever authentication mode, external data/model providers, upload formats, artifact formats, deployment topology, permission mappings, or production data classification changes, and after any security incident or material dependency advisory.
